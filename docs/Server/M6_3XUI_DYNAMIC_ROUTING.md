# M6 — динамическая маршрутизация TCP inbound 3x-ui и Remnawave

**Статус:** требования СОГЛАСОВАНЫ; сквозная автоматическая интеграция НЕ ПОДТВЕРЖДЕНА.  
**Проект:** Tervon TCP Bridge (не Tervon Federation).  
**Ветка:** `work/m6-android-ingress`. **HEAD при составлении:** `11618523c6e75bb7dc16e9c2a057cbed25a4f10d` (до добавления этого документа).  
**Область:** только серверная маршрутизация M6. Общий `docs/DEVELOPMENT_PLAN.md` остаётся действующим; исторические аудиты не являются текущим контрактом.

## 1. Утверждённый контракт

1. **Единственный источник состава inbound:** действующие включённые TCP inbound выбранной панели (**3x-ui API или Remnawave API**), обязательно сверенные с фактически применёнными обработчиками Xray. `server.json` — результирующая политика Bridge, а не источник перечня VPN-портов.
2. **Ключ маршрута — точный TCP-порт** подтверждённого inbound. Не использовать фиксированные идентификаторы `vpn`, `vpn-xhttp`, ручную `tcp_routes` или сопоставление по содержимому VPN-трафика. Внутреннее представление имени сервиса Bridge должно однозначно соответствовать порту; конкретный формат требует сверки с действующим контрактом Discovery/ядра перед реализацией.
3. **Один экземпляр Bridge обслуживает много клиентов и портов.** Каждое TCP-подключение имеет независимый двунаправленный поток. VLESS TCP, Trojan TCP и VLESS XHTTP передаются одинаково как непрозрачные TCP-байты. Содержимое, Host/SNI и внутренний протокол Bridge не интерпретирует.
4. **Один владелец управления:** существующий процесс `m6-auto-registrar` отвечает за enrollment и синхронизацию маршрутов/ACL. Не создавать второго демона, независимого writer или параллельного механизма регистрации.
5. **Одно атомарное поколение:** полные `routes + authorized` подготавливаются и применяются совместно; подтверждение — точный digest поколения от действующего Decapsulator. При добавлении/удалении подтверждённых inbound ACL уже зарегистрированных отпечатков сертификатов соответствует текущему проверенному набору портов. Не создавать сертификаты/отпечатки из данных панели.
6. **Сохранение действующих сессий:** обновление поколения не разрывает уже установленные TCP-потоки; новые запросы на неизвестные/неподтверждённые порты отклоняются. Не вводить глобальную блокировку data plane.
7. **Отказы:** ошибки API выбранной панели, Xray, backend и применения/ACK изолируются. Временный сбой чтения панели не равен доказанному удалению inbound. Неопределённый результат записи политики требует безопасного отказа для нового Discovery до выяснения действующего поколения. Никаких неподтверждённых маршрутов.
8. **Безопасность:** сохранить TLS 1.3, HTTP/2, mTLS, ACL, проверку идентичности целевого Docker Decapsulator и секреты только на сервере. Пределы нагрузки определять испытаниями, не придумывать числа.

## 3. Незавершённые привязки в том же модуле

- Получать HTTPS base URL выбранной панели из защищённых параметров установки, введённых оператором; не обнаруживать адрес панели автоматически. Формат существующего credential файла подтверждён оператором: `Authorization: Bearer …`.
- Подключить `SelectedBridgeInbounds` к единственному Registrar.
- Подключить **достоверный live** `AppliedXrayEvidence`, а не только парсинг конфигурации или статический PID.
- Привязать `RoutePolicyApply` к атомарной записи полной конфигурации и точному ACK **проверенного** действующего Decapsulator, без второго writer.
- Убрать зависимость динамической регистрации от стартового статического списка сервисов и обеспечить согласованное чтение подтверждённого поколения.
- Определить проверяемую политику периодического обновления и поведения при сбоях на основании действующего runtime, не вводя произвольный интервал или новые службы.

## 4. Комплексная приёмка

1. Изменение состава inbound выбранной панели (добавление, отключение, удаление) отражается в **подтверждённом** поколении Bridge без ручных имён маршрутов; неподтверждённый порт не публикуется.
2. VLESS TCP, Trojan TCP, VLESS XHTTP на разных портах и несколько одновременных клиентов на одном порту проходят реальный двунаправленный TCP E2E.
3. Атомарность routes+ACL, точный ACK, отсутствие потери сертификатов, сохранение уже открытых сессий при смене поколения.
4. Отказы API/Xray/backend/ACK, гонки enrollment ↔ sync, повторное поколение, отрицательные проверки mTLS/ACL, отсутствие утечек секретов.
5. Unit/integration/race, проверка соответствия действующему исходному commit, затем отдельно согласованные испытания Homeserver/Android. Нагрузочные лимиты — только по измерениям.

**Критерий PASS:** проверены исходники, тесты и фактическая E2E работа на одном установленном поколении; документация и commit соответствуют результатам. До этого статус **IN_PROGRESS / BLOCKED для непроверенных runtime bindings**.

## 6. Универсальность установки и поддержка Remnawave — СОГЛАСОВАНО 2026-11-24

- Один бинарник Registrar и общий координатор для 3x-ui и Remnawave; различается только адаптер получения inbound. Для Remnawave учитывать назначенный конкретному узлу профиль и активированные на нём inbound, не глобальный список центральной панели. Оба адаптера обязаны сверять данные с live Xray соответствующего узла.
- Запрещены привязки в исходниках к Homeserver или другому конкретному серверу: IP, домен, порт панели, gRPC endpoint, PID, VPN-порты, количество inbound, имя/ID Docker-контейнера, абсолютный путь установки, фиксированные имена маршрутов vpn/vpn-xhttp.
- Параметры конкретной установки получать из действующей конфигурации и обнаруженных runtime-данных. Актуальный HTTPS base URL панели (включая изменяемый порт и API base path) задаётся оператором при установке и обновляется в защищённой конфигурации; смена порта не требует перекомпиляции Registrar, ручного изменения маршрутов или перезапуска Bridge. PID Xray и gRPC endpoint определяются динамически; идентичность Decapsulator проверяется по параметрам установки.
- Тот же бинарник должен работать при переносе на другой поддерживаемый сервер без изменения исходников и перекомпиляции. Сохраняются enrollment, mTLS, ACL, атомарное поколение, exact ACK, независимые TCP-потоки и последняя подтверждённая политика при временном отказе чтения.
- Дополнительная обязательная приёмка: обе панели, смена порта панели, перезапуск Xray с новым PID, другая установка с отличающимися параметрами, динамическое добавление/удаление inbound и одновременные клиенты. Никаких изменений работающих служб без отдельного согласования.
- Статус требований: СОГЛАСОВАНО; реализация универсальных runtime bindings и Remnawave, испытания и PASS не подтверждены. Исторические наблюдения Homeserver не являются значениями по умолчанию или константами реализации.

## 7. Подключение панели при установке — СОГЛАСОВАНО 2026-11-24

- Установщик запрашивает тип панели (3x-ui или Remnawave), полный HTTPS base URL с портом и базовым путём, API-токен. Проверяет подключение и сохраняет параметры защищённо, без вывода токена.
- Для Remnawave однозначно определять обслуживаемый узел. Registrar читает параметры установки; автоматическое обнаружение адреса панели отменено. Автоматически обнаруживаются inbound-порты и live Xray.
- Изменение адреса, порта или токена выполняется обновлением параметров подключения без перекомпиляции или переустановки Bridge. Остальной контракт M6 неизменен.
- Статус: СОГЛАСОВАНО, реализация и PASS не подтверждены.
