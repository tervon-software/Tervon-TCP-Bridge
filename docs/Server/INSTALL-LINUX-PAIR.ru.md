# Tervon TCP Bridge между двумя Linux-серверами

На обоих узлах запустите `sudo ./install.sh` из ветки `work/m6-android-ingress` и выберите **2) Linux → Linux**.

| Узел | Роль | Что делает |
| --- | --- | --- |
| Сервер, где находится приложение или Xray, который **отправляет** TCP-трафик | **Encapsulator** | Слушает локальный порт и переносит TCP через Bridge. |
| Сервер, который **принимает** Bridge и может подключиться к конечному сервису | **Decapsulator** | Принимает mTLS, проверяет сертификат клиента и подключает его к настроенному TCP backend. |

```text
Приложение → 127.0.0.1:10080 (Encapsulator)
    → bridge.example.net:18443 (Decapsulator) → TCP backend
```

Для каждой роли доступны `native` и `docker`. Их можно комбинировать. У обоих узлов должны быть Linux x86-64, systemd, Python 3.11+, OpenSSL и curl. Для Docker нужны Docker Engine и Compose v2. Межсерверному режиму достаточно опубликованного ядра v1.0.2-m6 и статической пары маршрута и ACL. Registrar, панель и nginx Discovery относятся к режиму Android.

## 1. На отправляющем сервере создать CSR

```bash
git clone --branch work/m6-android-ingress git@github.com:tervon-software/Tervon-TCP-Bridge.git
cd Tervon-TCP-Bridge
sudo ./install.sh
```

Выберите **2 → encapsulator → prepare**. Передайте администратору принимающего узла файл `/etc/tervon-pair-encapsulator/client.csr` по доверенному каналу. Закрытый ключ остаётся в `config/pki/client.key` на отправляющем сервере.

## 2. На принимающем сервере установить Decapsulator

Клонируйте тот же репозиторий и запустите `sudo ./install.sh`. Выберите **2 → decapsulator → native или docker**. Введите DNS-имя, внешний TCP-порт, имя сервиса, адрес и порт backend и путь к полученному CSR.

- **Native:** если backend слушает на самом хосте, адресом может быть `127.0.0.1`.
- **Docker:** для backend на хосте выберите `host.docker.internal` и убедитесь, что сервис слушает на доступном контейнеру интерфейсе. Loopback внутри контейнера относится к контейнеру.
- Откройте выбранный транспортный TCP-порт для отправляющего сервера в сетевом периметре. Установщик ставит службу и сертификаты, а доступность через внешний firewall или NAT проверяется отдельно.

Установщик создаёт серверный CA и CA для клиентских сертификатов, подписывает CSR, добавляет отпечаток выпущенного сертификата в ACL выбранного сервиса и включает службу Decapsulator в автозапуск. Передайте назад **только** `client.crt` и `server-ca.crt` из `/etc/tervon-pair-decapsulator/export/`.

## 3. На отправляющем сервере запустить Encapsulator

Ещё раз запустите `sudo ./install.sh`, выберите **2 → encapsulator → activate → native или docker**. Укажите **то же DNS-имя Decapsulator, внешний порт и имя сервиса**, локальный TCP-порт и каталог с полученными сертификатами. Установщик проверит соответствие сертификата ключу, настроит транспорт и включит службу в автозапуск.

Теперь приложение на этом же хосте подключается к `127.0.0.1:<локальный-порт>`. Для полной проверки выполните через этот порт обычную операцию целевого TCP-сервиса и убедитесь, что пришёл ожидаемый ответ. Активная служба сама по себе ещё не проверяет весь маршрут.

`sudo ./install.sh --check` проверяет ввод и доступные файлы для выбранного этапа без установки. Ролям соответствуют `tervon-pair-encapsulator.service` и `tervon-pair-decapsulator.service`.

## Статус проверки

Локально проверены генерация CSR, подпись, проверка соответствия ключа и обмен TCP через два процесса Bridge с TLS 1.3, HTTP/2 и mTLS. В тестовой среде команды управления службами подменены. Приёмка на двух отдельных серверах, запуск Docker и проверка автозапуска после перезагрузки остаются открытыми.
