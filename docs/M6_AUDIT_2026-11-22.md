## Утверждённые ограничения

Сохранять выпущенное ядро Linux Bridge v1.0.1 и ранее подтверждённые функции; Android M6 остаётся текущим модулем. Не привязывать VPN endpoint, порт, домен, backend или имя протокола к фиксированному значению. Список разрешённых TCP backend должен соответствовать действующей конфигурации; транспортные служебные localhost-адреса и порты, полученные от ОС, не являются hardcode удалённого сервера. Действующий источник для Android — выбранный профиль/подписка, discovery — аутентифицированный HTTPS; Go передаёт непрозрачный TCP-поток без разбора VPN-протокола.

## Дефекты методики, установленные аудитом

1. Код ошибки `BRIDGE_SERVICE_UNAVAILABLE` означает отсутствие ключа выбранного **портового значения** в карте. Это не подтверждает неисправность прямого VLESS TCP, TLS или работающего Linux Bridge. Прежде прежние отчёты смешивали эти этапы. При восстановлении нужно получить **обезличенную пару** `selected profile transport / port present in discovery` и причину отказа, не публикуя реальные адреса или конфиденциальные подписки.
2. Тесты `BridgeVlessRoutePlanTest.kt` проверяют синтетические Endpoint/port и `decide()`; они **не проверяют**, что Android реально выбрал правильный proxy outbound из приложения, что `tcp_routes` соответствуют профилю, или что Xray корректно подключается через Go. `BridgeXrayConfigRouteTest.kt` тоже standalone, а не E2E на устройстве.
3. Исходники, установленные в `/opt/tervonvpndpi`, не все представлены в ветке как обычные Kotlin-файлы: `BridgeCoreManager.kt`, `BridgeRuntimeControl.kt` проверялись ранее по предоставленному выводу/архиву, а не повторным чтением текущего дерева Homeserver. **Нельзя** считать аудит Android завершённым без сверки точного полного исходника приложения с наложенными изменениями.
4. Запущенный регистратор формирует карту при старте, поэтому Xray ↔ Bridge ↔ discovery могут расходиться при последующих изменениях. Нельзя автоматически переписывать живые конфигурации без отдельного безопасного решения. Нужна доказательная проверка действительного набора маршрутов, не просто одинаковости снимков.
5. Значения локального порта, получаемые через `ServerSocket(0)`, не являются надёжной **резервацией** до последующего `net.Listen`: между освобождением порта и запуском Go есть TOCTOU окно. Это риск запуска/конкуренции, **не доказанная причина текущей ошибки**. Выделенный диагностический код `BRIDGE_LISTENER_UNAVAILABLE` уже предусмотрен.
6. Частичная попытка патча диагностики и косметические изменения схемы discovery ранее были отражены как «исправления», но runtime доказательств нет. До испытаний нельзя утверждать, что они решили пользовательскую проблему.

## Выборочное сохранение

**Кандидаты для сохранения:** неизменённый выпущенный Go v1.0.1; защищённая схема PKI/mTLS и получение сертификата по активной подписке после проверки; протокольно-независимый Go TCP byte stream; динамическое извлечение endpoint из профиля; валидаторы и негативные тесты; сохранение оригинальных Xray TLS/HTTP identity. Статус всех Android-кандидатов **REVIEWED ONLY**, не PASS.

**Не переносить вслепую:** существующие installer overlays, неизвестную последовательность патчей, жёсткие запечатанные снимки backend конфигурации, вывод `LOCAL_ROUTE_READY` как доказательство data-plane, диагностический патч до выяснения CODE 1.

## Дальнейший аудит в рамках утверждённого M6 (не выполнен)

1. Восстановить карту **реально установленного Android**: `BridgeCoreManager`, `BridgeRuntimeControl`, `BridgeSubscriptionBinding`, Xray config generation, VPN service, DNS/HEV, подписка/парсеры, интеграционные точки переключателя; сверить их с кодом GitHub и HEAD Homeserver. Не изменять исходники в этом шаге.
2. На реальных **обезличенных** входных параметрах воспроизвести ветку `BRIDGE_SERVICE_UNAVAILABLE`: сравнить выбранный `proxy` endpoint и аутентифицированный discovery, выявить, почему порт отсутствует в карте. Не заменять порт другим автоматически.
3. Отдельно исследовать XHTTP/Trojan: граница локального TCP → Go TLS/HTTP2 → серверный Decapsulator → Xray backend, собрав существующие диагностические наблюдения без модификации сервисов.
4. После законченного аудита согласовать точечный план сохранения/замены компонентов, критерии FAIL/PASS и только затем править код с тестами, документацией и commit.

**Итог:** `M6_AUDIT_GITHUB=PARTIAL`; `M6_AUDIT_RUNTIME=NOT_DONE`; `VLESS_TCP_BRIDGE_ENABLE=FAIL_OBSERVED`; `XHTTP_TROJAN_BRIDGE_DATA_PLANE=FAIL_OBSERVED`; `CAUSE=NOT_CONFIRMED`; `LIVE_SERVICES=UNCHANGED`. Документ — фиксация аудита, а не изменение утверждённой архитектуры или функций.
