# M6 — подписываемый каталог Bridge-серверов v1

**Статус: код изолированно записан; APP_RUNTIME_NOT_INTEGRATED / ANDROID_BUILD_NOT_RUN.** Доверенный ключ ещё не выпущен и не закреплён в APK.

## Формат доверия

Принят вариант 2 — обновляемый **подписанный каталог**, при котором Android заранее доверяет фиксированному публичному Ed25519-ключу подписанта. Этот ключ не должен поступать из самого каталога, произвольной VPN-подписки или camouflage SNI. Приватный ключ подписанта хранится отдельно и никогда не включается в исходники, APK или работающий Decapsulator.

Envelope JSON: обязательные поля `format` (значение `tervon.bridge.catalog.envelope.v1`), `key_id`, `payload_b64`, `signature_b64`. Base64 — standard encoding с padding. Ed25519 подписывает **точные bytes** UTF8("Tervon-Bridge-Catalog-v1") + byte 0x00 + decoded payload bytes. Не требуется неоднозначная JSON-канонизация: подпись сверяется с исходным payload без пересериализации.

Decoded JSON payload строго содержит:
- `version: 1`;
- `serial` — положительный монотонно возрастающий номер;
- `issued_at`, `expires_at` — Unix секунды, окно не более 30 дней;
- `servers` — массив 0–256 записей.

Каждая запись содержит обязательные `id`, `endpoints` (массив выбранных VPN host+port), `tls_name`, `bridge_url` (HTTPS), `enrollment_url` (HTTPS), `server_ca_pem`. CA здесь служит для проверки **TLS-сервера Bridge**, а не для выдачи клиентских сертификатов. Endpoints определяют офлайн-сопоставление профиля с подписанным Bridge-server ID. Дубли ID и host:port, неизвестный ключ, неверная подпись, несовпадающий TLS host, невалидный HTTPS, лишние JSON-поля — отказ. Пустой **подписанный** список серверов позволяет отозвать сразу все сопоставления.

## Локальный кеш и отключённый Bridge

Android получает подтверждённый каталог через будущий защищённый механизм обновления; текущая библиотека **не делает запросов, DNS, выдачи сертификатов или переключения VPN**. Проверенная версия хранится через Android AtomicFile в noBackupFilesDir. Повреждённое или просроченное содержимое не является доверенным. Новая подпись с меньшим `serial` или изменёнными байтами при одинаковом `serial` отвергается. Повторный приём тех же байтов идемпотентен; ошибка обновления не перезаписывает кеш.

При ручном DPI OFF не регистрировать устройство, не обновлять каталог по сети, не пробовать Bridge. При ON офлайн-адрес выбранного VPN-профиля сопоставляется с каталогом и передаётся ранее проверенному `BridgeServerReconciler`. Если сертификата нет — регистрация только отдельной кнопкой пользователя. Ошибка DNS не превращает известный сервер в неизвестный.

## Код и границы проверки

- `stage4/BridgeSignedServerCatalog.kt`: Bouncy Castle Ed25519, строгая проверка подписанного payload и AtomicFile cache.
- `xui/catalog/sign.go`: офлайн-библиотека Go stdlib Ed25519, не работает как HTTP endpoint.
- `xui/catalog/sign_test.go`: проверка подписи, domain separation, tamper rejection и невалидных входов.
- `stage4/install_signed_catalog.py`: только guarded staging Android verifier и reconciler, не заменяет отличающиеся файлы и не трогает действующие службы.

**Остаётся:** подтверждённые Go CI тесты и Android-компиляция; выпуск и pin доверенного публичного ключа; механизм защищённого получения каталога; полная проверка server CA; интеграция с реальным профильным событием и ручной аутентифицированной регистрацией; реальный Xray route + socket protect + rollback и Android E2E. Не заявлять PASS за пределами полученных логов.

Ограничение: serial rollback guard реализован в обычном app-private хранилище. Физический откат данных приложения атакующим с доступом к устройству этим механизмом отдельно не предотвращается.


## M6 — офлайн-выпуск подписанного файла без создания production-ключа

Добавлена команда `xui/cmd/catalog-sign` (в составе прежнего Go-модуля; никаких сетевых интерфейсов или новых служб). Используется существующий **Ed25519 PKCS#8 PEM** из защищённого файла, переданный оператором явно через `-key`; утилита не генерирует и не печатает ключи. Проверяются права файла (никаких разрешений группе/остальным), обычный файл, отказ от символьных ссылок и подмены inode, ограничение размера; для ключа требуется unencrypted PKCS#8. Это означает, что режим `0600` защищает доступ правами ОС, но **не шифрует приватный ключ на диске**: пригодность такого хранения для production и фактическая защищённая директория требуют отдельного решения. Использование выделенного офлайн-носителя/изолированного окружения предпочтительно, процесс запускается только оператором, без постоянной службы.

Пример формы запуска (НЕ выполнять с демонстрационным ключом): `go run ./cmd/catalog-sign -key <защищённый-путь-PKCS8> -payload <проверенный-json> -key-id <утверждённый-id> -out <новый-файл-envelope>`. Выход создаётся только при отсутствии файла, режим `0600`, при ошибке подписи он не создаётся. Утилита подписывает JSON, но не публикует каталог и не утверждает доверие подписанных данных; содержание, serial и CA требуют независимой проверки до подписания.

Изолированный Go 1.23.2 `go test -race -count=1 -v ./...` для эквивалентной локально воспроизведённой команды: 3 теста PASS (правильная подпись, запрет перезаписи, неправильные права и symlink, плохой JSON). Запуск CI по текущему commit и фактическая production-подпись ещё не подтверждены. Не генерировать production-ключ до согласования защищённой среды хранения и процедуры публичного pin в APK; не делать `go run` под пользователем действующего Bridge/Xray.

## Универсальные расположения Linux (FHS; согласовано)

Tervon TCP Bridge — переносимое открытое ПО. Пути ниже являются **настройками по умолчанию**, а не привязкой к Homeserver, Debian, systemd, Docker или конкретному пользователю:

| Роль | Расположение по умолчанию | Назначение |
|---|---|---|
| Узел Bridge | `/etc/tervon/bridge/` | конфигурация без приватного ключа подписи глобального каталога |
| Локальный серверный PKI | `/etc/tervon/bridge/keys/` | только локальные ключи конкретной установки, если нужны |
| Долговременное состояние узла | `/var/lib/tervon/bridge/` | учёт/кеш/данные сервера |
| Временные runtime-данные | `/run/tervon/bridge/` | необязательный runtime путь, на системах без `/run` переопределяется |
| Издатель каталога — *только он* | `/etc/tervon/bridge/keys/catalog-ed25519.pk8.pem` | приватный ключ издателя, **не разворачивать на обычных узлах** |
| Издатель каталога | `/var/lib/tervon/bridge/catalog/catalog.json` | проверенный исходный JSON перед подписью |
| Издатель каталога | `/var/lib/tervon/bridge/catalog/catalog.signed.json` | созданный подписанный envelope; публикация отдельно |

В `catalog-sign` все три файловых пути по-прежнему переопределяются параметрами `-key`, `-payload`, `-out`. **`-key-id` обязателен**. Отсутствующий каталог/ключ/директория не создаются автоматически. Ключ никогда не встраивается в бинарник или репозиторий. Обычному серверу Bridge для проверки/раздачи подписанного каталога достаточно **публичного** ключа — глобальный приватный ключ на нём не нужен.

Использование путей /etc и /var/lib соответствует FHS, но не является системным менеджером секретов. Проектные каталог и файлы требуют предварительного безопасного создания установщиком/оператором (directory `0700`, private key `0600`, отдельные права на публикуемые данные). Расширения и контейнеры без доступа к системным каталогам должны использовать переопределённые пути; не пытаться записывать данные из APK на Linux-хост. Утилита пока читает **незашифрованный** PKCS#8 из защищённого файла, его шифрование на диске не реализовано и не должно декларироваться.

Существующие установки и сервисы не мигрируют автоматически. Старые локальные пути не удаляются и их совместимость не меняется; это дефолты **нового инструмента подписания** на новых установках.

## M6 — закрепление публичного ключа в Android APK (исходник подготовлен)

Добавлен `stage4/BridgeCatalogTrustAnchors.kt`. Он загружает публичные Ed25519-ключи **только из APK asset** с постоянным именем `bridge_catalog_trust_v1.json`. Отсутствие или нарушение структуры asset приводит к явной ошибке; никакого автоматического доверия к сетевому ключу, URL подписки или тестовому ключу нет. До фактической поставки проверенного asset этот модуль работает в режиме **fail closed**, а Bridge не может использовать обновлённый каталог. Само наличие класса НЕ означает включение обхода DPI.

Содержимое подлинного asset должно быть подготовлено издателем APK при сборке после подтверждения владения приватным ключом. Формат:

```json
{
  "format": "tervon.bridge.catalog.trust.v1",
  "keys": {
    "<утверждённый-key-id>": "<base64-кодированный 32-байтный Ed25519 PUBLIC key>"
  }
}
```

Это **шаблон формата**, не рабочий asset. Используются стандартный Base64 с padding и 1–4 доверенных ключа (для будущей контролируемой ротации). Приватный PKCS#8, пароль и подпись каталога внутрь trust asset не включать. При отсутствии production-ключа **не создавать файл-заглушку** и не внедрять демонстрационную пару в релиз. Ключи не читаются из `SharedPreferences`, `noBackupFilesDir` или ответа HTTPS, то есть обычное обновление каталога не может подменить корень доверия. Изменение самого набора ключей пока требует подтверждённой сборки и подписи APK; отдельный протокол ротации ключей **не реализован**.

Проверенный путь создания экземпляра verifier: `BridgeCatalogTrustAnchors.openVerifiedCatalog(context)`, который использует встроенные ключи. Функция не скачивает каталог и не запускает Bridge. Продолжаем использовать уже проверенный `BridgeSignedServerCatalog`, которому передаётся неизменяемая по источнику доверенная таблица. Новый загрузчик добавлен в существующий guarded installer `stage4/install_signed_catalog.py`: `--check` / `--apply` установят только отсутствующий Kotlin-файл, не перезаписывая отличающийся оригинал. Trust asset намеренно не создаётся установщиком.

**Статусы:** `ANDROID_TRUST_LOADER_SOURCE_COMMITTED`; `ANDROID_TRUST_LOADER_COMPILE_NOT_CONFIRMED`; `PRODUCTION_TRUST_ASSET_NOT_PROVISIONED`; `CATALOG_UPDATER_NOT_IMPLEMENTED`; `DEVICE_CATALOG_VERIFICATION_NOT_TESTED`; `VPN_ROUTE_UNCHANGED`. До проверки этого изменения компиляция предыдущих модулей остаётся PASS без повторного запуска.

## M6 — выпуск ключа издателя на любой Linux (код, не выполнение)

Добавлена отдельная **офлайн** команда `xui/cmd/catalog-keygen`: она по явному запуску создаёт новую пару Ed25519 через Go `crypto/rand`, сохраняет PKCS#8 PEM приватного ключа (`0600`) и публичный `bridge_catalog_trust_v1.json` (`0644`), совместимый с `BridgeCatalogTrustAnchors.kt`. Ключевые данные не выводятся на экран. Печатается SHA-256 отпечаток **только публичного ключа** для независимой проверки перед закреплением в APK. Режим по умолчанию: ключ `/etc/tervon/bridge/keys/catalog-ed25519.pk8.pem`, публичный ресурс `/var/lib/tervon/bridge/catalog/bridge_catalog_trust_v1.json`. Доступны опции `-key`, `-trust-out`, `-key-id`; все пути переопределяются, никаких обязательных systemd/TPM/Docker.

**Защита от ошибочного запуска:** каталоги должны уже существовать, директория приватного ключа должна быть закрыта группе/остальным (обычно `0700`), существующие файлы и символические ссылки на целевых путях не перезаписываются (`O_EXCL`). При невозможности создать публичный ресурс только что созданный приватный файл удаляется. Команда не подключается к работающим VPN-службам и не публикует ключи.

**Ограничение:** в текущем формате приватный PKCS#8 на диске не шифруется, хотя ОС ограничивает доступ к нему. Нужна защищённая среда оператора/издателя, а не перенос приватного ключа на каждый обычный Bridge-сервер. Безопасность физического носителя, резервирование и восстановление при потере требуют отдельной эксплуатационной процедуры. Production-пара пока не создавалась. Подписанный каталог на Android начнёт проверяться только после независимой сверки полученного публичного отпечатка, включения реального JSON в ресурсы *подписанного APK* и проверки на устройстве; генератор сам ничего туда не устанавливает.

**Тестирование:** локально созданный эквивалентный Go-код (`go test -race -count=1 -v ./...`) — 3 теста PASS: совпадение публичного/приватного ключа и отпечатка, отказ от небезопасной директории и невалидного ID, отказ от перезаписи и откат при занятом публичном пути. Запуск тестов **точных GitHub-файлов на Homeserver / GitHub CI ожидает подтверждения**. Не выдавать генерацию production-ключа за выполненную.

## M6 — установка публичного ключа издателя в APK без привязки к Linux-хосту

Добавлен `stage4/install_catalog_trust_asset.py` — **только публичный ключ**, без работы с закрытым ключом, серверными службами, Gradle, сетью или VPN. Отдельная Linux-машина издателя может передать публичный `bridge_catalog_trust_v1.json` на машину сборки приложения по выбранному оператором доверенному каналу. Публичный материал сам по себе не является секретом, но должен пройти **независимую сверку** SHA-256 по открытому 32-байтному Ed25519-ключу. Именно этот отпечаток выдаёт ранее проверенный `catalog-keygen`.

Установщик получает `--app-root`, `--public-asset`, `--expected-public-sha256` и один из `--check` / `--apply`. Сверяет точную JSON-схему и публичный отпечаток, отвергает дополнительные неопознанные ключи, дубли JSON-полей, повреждённый Base64, несовпадающий SHA и файл-заменитель. Для **первоначального выпуска** разрешён ровно один публичный ключ. Поддерживаемые Android 1–4 ключа остаются за отдельным контролируемым протоколом ротации; дополнительные ключи нельзя принимать автоматически по отпечатку только одного ключа. Запись только в `android/app/src/main/assets/bridge_catalog_trust_v1.json`; никакой замены отличающегося существующего asset. Режим `--check` не создаёт каталоги и файлы.

Код и тестовые сценарии `stage4/test_install_catalog_trust_asset.py` опубликованы, но тесты точного GitHub-коммита ещё не запускались. **Никакого настоящего ключа пока нет**, устанавливать демонстрационные/случайные публичные данные в релиз нельзя. Использовать утилиту только после явного выпуска и проверки production-пары; ключ никогда не генерируется самим установщиком.

Это подготовка для финального этапа доверия. Она не включает сетевое обновление каталога, ручную регистрацию клиента, mTLS или маршрутизацию Xray.

## M6 — утверждённая децентрализованная архитектура (ИСПРАВЛЕНИЕ, 2026-11-20)

**Этот раздел отменяет прежнее предположение о едином глобальном издателе и обязательном APK-pinned ключе.** На каждом Linux-сервере, где установлена панель **Remnawave либо 3x-ui** и чей TCP-трафик нужно проводить через Bridge, создаётся своя пара Ed25519. Приватный ключ остаётся только на ЭТОМ сервере, в универсальном по FHS месте `/etc/tervon/bridge/keys/catalog-ed25519.pk8.pem` (с переопределяемым путём и ограниченным доступом). Он используется локально для подписи каталога **своего** сервера. У каждого сервера независимые ключи и номера `serial`. Никакого центрального уполномоченного издателя и обязательного общего APK-ключа нет.

**Первичное доверие:** Android должен получить публичный ключ конкретного сервера и **отдельно подтвердить его SHA-256 отпечаток через действительно доверенный канал**. Отпечаток из того же непроверенного сетевого ответа не подтверждает подлинность, автоматическое TOFU запрещено. Точное сопряжение с авторизованной панелью/QR/интерфейсом пока не реализовано. Нельзя выводить доверенный server ID из camouflage SNI, произвольного URL или неподтверждённой подписки. До подтверждения ключа Bridge для этого сервера не включается, обычный VPN сохраняется.

Новый `stage4/BridgeServerCatalogTrust.kt` хранит ключ по **стабильному доверенному server ID** в app-private `noBackupFilesDir/bridge-server-catalog-trust-v1/<sha256(serverId)>.json`. Метод `confirm(serverId,keyId,publicKeyBase64,independentlyVerifiedSha256)` проверяет длину/формат/отпечаток, не создаёт доверие из одного сетевого ответа и отказывается молча заменять уже закреплённый ключ. Метод `pinned(serverId)` возвращает только ранее явно закреплённый ключ. `openVerifiedCatalog(context,serverId)` создаёт прежний `BridgeSignedServerCatalog`, но только с ключом соответствующего сервера.

Существующий `BridgeSignedServerCatalog.kt` минимально расширен необязательным параметром `trustedServerId`: при его наличии кеш подписанного каталога тоже разделяется по SHA-256 server ID, а подписанный `servers` может содержать **только запись с таким ID** либо пустой список для отзыва. Чужой сервер не может быть разрешён сертификатом подписи другого. Срок, signature, rollback-сериал и прочие проверки остаются прежними. Старый конструктор без scope оставлен исключительно для совместимости изолированных исходников — **не использовать** для реальной регистрации и VPN routing.

Ранее созданные `BridgeCatalogTrustAnchors.kt` и `install_catalog_trust_asset.py` представляли модель общей APK-публикации. **Не используем их в новой децентрализованной цепочке**; файлы не удаляем из истории и не переписываем прежний APK без испытаний. Новый guarded installer `stage4/install_per_server_catalog.py` ставит файл per-server trust и переводит прежний verifier только при точном соответствии старому исходнику commit `1db955240076b34ff43efafe9cbfeeeceaad15be`. Не перезаписывает сторонние изменения, не мигрирует автоматически неизвестные ключи и не создаёт работающих ключей/каталогов.

**Граница готовности:** `DECENTRALIZED_SOURCE_COMMITTED`; `ANDROID_BUILD_NOT_RUN`; `FIRST_FINGERPRINT_CONFIRMATION_UI_NOT_IMPLEMENTED`; `PANEL_AUTHENTICATED_BOOTSTRAP_NOT_IMPLEMENTED`; `DEVICE_SIGNATURE_E2E_NOT_TESTED`; `VPN_ROUTE_NOT_IMPLEMENTED`. Ранее подтверждённые Go race PASS и Stage4 CSR PASS не нужно повторять. Последующие шаги: сборка новых Kotlin-файлов; затем безопасный согласованный способ предъявить отпечаток из уже аутентифицированной панели и ручное подтверждение на Android; после этого — регистрация сертификата, локальный Bridge, защищённый внешний сокет и переключение Xray.

## M6 — ручное подтверждение отпечатка для отдельного сервера (источник в GitHub)

Согласованный децентрализованный сценарий: сервер с Remnawave или 3x-ui хранит собственную закрытую пару Ed25519 в FHS; Android закрепляет публичный ключ **только** для доверенного стабильного `serverId`. Добавлена отдельная Flutter-страница `stage4/bridge_server_trust_screen.dart` с полями server ID, key ID, публичный Ed25519 Base64 и **независимо проверенный** SHA-256. Кнопка разблокируется после отдельной явной отметки пользователя, что отпечаток получен через доверенный канал администратора. Kotlin `BridgeControlChannel` получает новый метод `confirmServerCatalogKey`, передающий значения существующему `BridgeServerCatalogTrust.confirm()`; входящий флаг согласия обязателен, ошибки не раскрывают входные ключи. Это **только ручная операция доверия**, не сетевой bootstrap, не выдача CSR/сертификата и не изменение маршрута VPN.

Новый guarded `stage4/install_server_trust_ui.py` проверяет оригинальные уникальные блоки Flutter экрана Bridge Settings и Android MethodChannel, наличие уже скомпилированного `BridgeServerCatalogTrust.kt` и отсутствие отличающегося нового экрана. Изменяет два существующих файла и создаёт одну Dart-страницу; `--check` не записывает ничего. Установщик не затрагивает HEV, Xray, работу Bridge, подпись APK и публикацию. **Перед применением нужно сверить текущие файлы приложения**, потому что доступный архив исходного Flutter-экрана исторический и другие изменения могли быть сделаны позже.

Принципиальное ограничение: чекбокс и совпадение отпечатка — это **не криптографическое доказательство**, что отпечаток действительно пришёл из авторизованной панели. Администратор/пользователь должен получить его через независимый доверенный канал. Публичный ключ и SHA-256 из одного непроверенного ответа нельзя считать основанием доверия. Встроенное подтверждение через аутентифицированные API 3x-ui/Remnawave **не реализовано**; оно потребуется перед автоматической регистрацией в массовом клиенте.

**Статус:** `MANUAL_TRUST_UI_SOURCE_COMMITTED`; `ANDROID_APPLY_NOT_RUN`; `ANDROID_COMPILE_NOT_RUN`; `ON_DEVICE_PIN_TEST_NOT_RUN`; `PANEL_AUTHENTICATED_BOOTSTRAP_NOT_IMPLEMENTED`; `NETWORK_CATALOG_UPDATER_NOT_IMPLEMENTED`; `VPN_ROUTE_UNCHANGED`.

## M6 — офлайн-самопроверка закрепления ключа непосредственно в Android

Добавлен `BridgeServerCatalogTrustSelfCheck.kt` и кнопка «Самопроверка доверия (без реальных ключей)» в `bridge_server_trust_screen.dart`. Диагностика вызывается **только по нажатию**, через `serverCatalogPinSelfCheck` в существующем `BridgeControlChannel`. Для проверки используется уникальный временный каталог в `cacheDir`, передаваемый через необязательный диагностический параметр `baseDir` существующего `BridgeServerCatalogTrust`; постоянное `noBackupFilesDir/bridge-server-catalog-trust-v1` не используется и не очищается. Тестовые 32-байтные публичные данные генерируются `SecureRandom` в памяти, приватные Ed25519-ключи не генерируются. Проверки: отказ при неверном SHA-256 без записи; успешное закрепление с правильным отпечатком; повторное открытие файла; идемпотентный повтор; отказ от изменения ключа или key ID; изоляция двух серверов. Временный каталог удаляется в `finally`. Ошибка выдаёт общий код без раскрытия ключей.

`stage4/install_server_pin_selfcheck.py` применяет четыре узко определённых изменения (один новый Kotlin-файл, обновление старого класса хранения, одной Flutter-страницы и ветки MethodChannel) только при совпадении ранее утверждённых исходников. Используется заранее фиксированная Git-история для сравнения старых версий. `--check` не меняет приложение, `--apply` требует успешной предварительной проверки. APK, работающие VPN/HEV/Xray и серверные ключи не изменяются.

Эта диагностическая проверка **не доказывает подлинность предъявленного пользователем отпечатка** и не запускает реальную проверку подписи серверного каталога — для этого потребуются доверенные данные конкретной авторизованной панели и испытания на устройстве. **Код сохранён в GitHub; тест непосредственно на Android и компиляция нового пакета ещё не подтверждены.**
