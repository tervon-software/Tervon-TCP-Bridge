## 4. Установленные проблемы документации и проекта

1. **313 KB append-only план** смешивал задачи, промежуточные FAIL/дальнейшие PASS и взаимоисключающие текущие статусы; рабочий план очищен и нормализован. Старые сведения доступны в Git commit history и датированном журнале, но не являются активными предписаниями.
2. `docs/M6_ANDROID_RECOVERY_BLOCKERS_20261121.ru.md` ранее утверждал, что enrollment не реализован и APK не собран, что уже опровергнуто результатами 22 ноября; документ **устарел**.
3. `integrations/android-ingress/README.ru.md` сообщал «discovery/enrollment — не реализовано»; на данном HEAD есть полноценный `xui/enrollment_http.go`, `cmd/m6-auto-registrar`, Android enrollment source; утверждение устарело.
4. `xui/cmd/m6-auto-registrar/main.go` по-прежнему публикует маршруты из `server.json`; `xui/route_sync.go` и `ConfirmedRouteStore` представлены отдельно. Существование исходников **не доказывает автоматическую live-синхронизацию**. Признаём разницу; не придумываем дефект Docker и не переписываем серверную часть наугад.
5. Legacy `prototype/bridge.go` ветки отличается от исходного выпущенного binary; использовать exact release provenance.
6. Android диагностика `UNKNOWN` скрывает стадию обрыва; локальная доступность listener не подтверждает передачу до backend.

## 5. Что подтверждено, чего нет, критерии продолжения

**Подтверждено:** Linux v1.0.2 released asset hash; operator Go Android ARM64 source build and install checks; Kotlin compile; Docker image/Compose/cutover; read-only panel–Xray–routes audit по прошлому операторскому результату; Android device NO INTERNET; GitHub presence dual old/new server route mechanisms.

**НЕ подтверждено:** фактический current SHA и содержание всех файлов установленного на Homeserver Android source после APK; фактический binary/параметры запущенного регистратора; wired-up `SyncVerifiedRoutes` в его runtime; Android → сервер mTLS/H2 → backend двусторонняя передача; пофайловое утверждение очистки Android.

**Стоп-линия:** никакого изменения Android-приложения, серверной инфраструктуры, версии/подписи, удаления кода до утверждения матрицы и актуального API contract. Следующий разрешённый шаг — сверить current Homeserver read-only repo/runtime provenance с исходниками GitHub и довести матрицу зависимостей для плана пересоздания Android M6. Исторические события оставлять как события, не выдавать старые статусы за нынешние.

### 8.1. Подтверждённые альтернативные пути управления

- **Нормальный toggle:** Flutter `bridge_settings_screen.dart` → MethodChannel `com.tervonvpndpi/bridge_control:setBypassEnabled` → `BridgeControlChannel.enroll` → существующее HTTPS discovery/CSR → `BridgeSubscriptionBinding.save` / `BridgeRuntimeSettings.setEnabled` → VPN restart → `BridgeVpnSession.prepare` → `BridgeRuntimeControl.launchClient` → `BridgeCoreManager.launch`.
- **Нормальная смена профиля:** `xray_service.dart` → `prepareBypassForProfile` → тот же `enroll` с `restart=false`, затем штатный restart Xray; `VpnForegroundService` вызывает `BridgeVpnSession.prepare` при пересоздании Xray config.
- **Альтернативный runtime control:** `BridgeRuntimeControl.register` всегда регистрирует **второй** MethodChannel `com.tervonvpndpi/bridge_runtime` с `installClientConfig/start/stop/status`. Он может вызвать `BridgeCoreManager.launch` напрямую, без `BridgeVpnSession.prepare` и без изменения `BridgeVpnSession.ownsProcess`. Отдельный `bridge_runtime_screen.dart` содержит вызовы этих методов, **но в архиве нет явного Dart import этого экрана**. Канал всё равно зарегистрирован; фактическое использование пользователем не подтверждено. **Статус: несогласованная альтернативная управляющая поверхность, кандидат для удаления/изоляции после согласования.** Не утверждать, что именно она сломала трафик.

### 8.2. Дублирование/противоречие конфигурации и статуса

- `BridgeRuntimeSettings.update` сохраняет `remoteUrl`, `service`, `serverName`, `localPort` в `tervon_bridge_settings_v1`; **обычный** `BridgeVpnSession.prepare` использует из preferences `enabled`, а endpoint/service берёт из `BridgeAutoEnrollmentHttp.discoveredParameters()`, `tcpRoutes[selected.port]`, локальный port получает из `ServerSocket(0)`. Поля settings не являются источником истины обычной TCP-маршрутизации. Это подтверждённое дублирование интерфейса, **не скрытый hardcode в основном data plane**.
- `BridgeRuntimeControl.status` возвращает `vpnRouteIntegrated=false` **константой**. `BridgeRuntimeSettings.snapshot` возвращает `runtimeIntegrated=BridgeVpnSession.active()` (локальный listener/процесс, **не E2E**). Эти два статуса логически различаются и не должны подаваться как единая проверка работоспособности.
- `BridgeVpnSession.active()` считает процесс RUNNING и флаг `active` достаточными, но последний выставляется после loopback dial и правки конфигурации, **до** подтверждения удалённого HTTP/2, mTLS, status=200 и backend. Status “ACTIVE” лишь local readiness.
- `BridgeVpnSession.prepare` по большинству исключений возвращает исходный direct JSON и ставит stage code; никаких доказательств, что локальный Bridge session добрался до сервера, такой fallback не даёт.

### 8.3. Разграничение действительно зашитого и намеренно фиксированного

- `BridgeAutoEnrollmentHttp` строит `https://<host текущей подписки>:443/.well-known/tervon-bridge` и не отправляет секретный путь/query подписки. **443 — фиксированный порт discovery по реализованному контракту**, не фиксированный backend VPN порт. Нельзя автоматически объявлять его ошибкой и менять без решения пользователя.
- `BridgeClientConfigBuilder` требует `/v2/stream`, `service` получает динамически, локальный port — от ОС. `/v2/stream` — версия транспортного endpoint, не протокольный hardcode.
- `BridgeXrayConfigRoute` сохраняет оригинальные HTTP Host/TLS SNI/authority при редиректе dial address на loopback. Проверяет структуру Xray JSON, включая `downloadSettings` XHTTP; он **не читает TCP payload**, однако это протокольно-осведомлённая *обвязка Xray config*, которую нужно оценить при минимизации.
- `VpnForegroundService` вызывает `addDisallowedApplication(packageName)` для собственного приложения при установке VPN. Это наблюдаемое исключение app traffic из VPN, но без реального network trace нельзя доказать, что каждый сокет внешнего Go процесса защищён.

### 8.4. Границы удаления по статическому поиску

По прямым текстовым вызовам среди `*.kt`/`*.dart` указанного snapshot:
- `BridgeVpnIntegration.kt` не имеет видимых внешних ссылок на имя класса; `bridge_runtime_screen.dart`, `bridge_server_trust_screen.dart` не имеют видимых Dart import из другого Dart файла; `BridgeCatalogTrustAnchors.kt` не имеет видимых внешних упоминаний.
- **Это кандидаты на дальнейшую проверку, не разрешение немедленно удалять:** могут существовать reflection/route/asset/XML/внешние источники вне snapshot.
- `BridgeServerCatalogTrust` вызывается из BridgeControlChannel (операторский метод подтверждения ключа) и self-check; не считать его неиспользуемым лишь потому, что пользовательский экран не импортирован.

**Дополнительные подтверждённые проблемы старой Android-обвязки:** два пути управления одним ядром; два несовместимых критерия статуса; необязательные хранимые endpoint/service поля при динамическом Discovery; недостаточная доказательная сила loopback readiness. **Корень существующего XHTTP EOF остаётся `UNKNOWN`.**

**Статус этой проверки:** `STATIC_SOURCE_AUDIT=PASS` для перечисленных фактов; `ACTUAL_HOMESERVER_ANDROID_FILE_HASHES=NOT_CHECKED`; `RUNNING_REGISTRAR_IDENTITY=NOT_CHECKED`; `M6_DEVICE_E2E=FAIL`; `FILE_DELETION=NOT_APPROVED`. Следующее — read-only provenance и матрица actual app file checksums; ничего не компилировать/устанавливать до решения об очистке.

### Что убрано из действующего руководства, что НЕ удалено из кода

- Действующий план очищен от исторической хронологии; старые документы об устаревших blockers удалены или помечены архивными, договор регистрации заменён актуальным; Stage4 README запрещает повторное применение legacy installers. Все исправления — **только GitHub docs**, старые коммиты остаются доступными.
- Семь файлов **не удалены** из реального Android-приложения. Утверждённая область замены не даёт права удалять ключи, сертификаты, серверный регистратор, Go ядро, Xray/VpnService, подпись, историю Git или менять рабочий сервер.
- Указанные SHA-256 — **проверка snapshot**, не hash действующего Homeserver. Фактический Android source и бинарник регистратора являются внешними оперативными доказательствами; в GitHub только по исходникам их установить нельзя.
- Прежде чем физически заменять файлы в Android app, получить read-only hashes/current source; если текущий файл отличается — не применять новую реализацию к старой копии и не притворяться совпадением.

### Критерии приёмки пересозданной обвязки

1. Один lifecycle owner и один однозначный UI/toggle control contract. Ни одного обходного process-start path.
2. Серверные протоколы/порты: актуальный 3x-ui API и сверка live Xray; отдельную `tcp_routes` не вводить. Не вводить hardcoded backend names/ports/domains и не заново разрабатывать API или сам Decapsulator.
3. Внутренний VPN TCP payload сохраняется побайтно; Xray JSON route изменяется только настолько, насколько требуется для dial 127.0.0.1 с сохранением оригинальных Host/SNI/authority.
4. Отдельные состояния `LOCAL_LISTENER_READY`, `REMOTE_H2_MTLS_ESTABLISHED`, `BACKEND_CONNECTED`, `DATA_TRANSFER_CONFIRMED`; ни один из них не называется E2E PASS до фактического двунаправленного обмена.
5. Комплексный изолированный тест random binary TCP + half-close/full-duplex, далее на Android VLESS TCP/XHTTP/Trojan и действительный интернет, включая выключение Bridge без регрессии обычного VPN.
6. Все тесты/исправления/документация и commit относятся к одному доказанному исходному состоянию. Flutter/Gradle/build status не заменяет device E2E.
